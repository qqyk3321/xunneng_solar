# 员工站版本记录

员工只读，由 Agent 维护数据库记录。把版本范围判断纳入代码修改，把历史记录核对纳入发布收尾。遵循用户当前授权；使用本技能不代表自动获得部署授权，也不要求对已经授权的发布重复确认。

## 先确认项目和现有记录

本技能位于项目根目录 `.codex/skills/staff-release-history/`；员工应用位于根目录下 `ticket-query-local/`。

- 阅读 [版本规则、数据库结构与 SQL 示例](../../../ticket-query-local/docs/release-history.md)。实际写入前核对现有迁移与线上 schema，文档示例中的版本号不是下一次发布的版本号。
- 员工版本库是 Supabase 项目 **`qxwngipzjddfeygswfzo`**。主站业务库 **`thiqsnscgdjwihcfpomw`** 不是版本记录的写入位置。使用现有受信任管理连接；不要把管理密钥放入客户端或文档。
- 使用 Supabase CLI 时显式指定员工目录，例如在项目根目录使用 `--workdir ticket-query-local`，先核对 linked project。不要直接沿用主站根目录的链接。
- 从 `public.staff_release_targets` 和 `public.staff_release_current` 查询实际目标、路径与当前版本；不要维护一份写死的页面清单。模板路由 `/submissions/[id]` 共用一个版本，不按客户生成版本。

## 判断本次应更新什么

| 实际上线变化 | 记录范围 |
| --- | --- |
| 单页功能、显示、交互或修复 | 该页面 `update`；平台版本不变 |
| 共享业务逻辑影响多个页面 | 各受影响页面分别 `update`；没有结构/布局变化时平台版本不变 |
| 公共导航或整体布局 | 平台 `structure` 或 `layout`；另有独立页面功能变化时再追加对应页记录 |
| 新增真实页面 | 新 target、该页初始 `v1.0` 的 `added`、平台 `structure` |
| 删除真实页面 | 保留 target，设置 `retired_at`，该页 `removed`、平台 `structure` |
| 页面路径改名 | 保持 target id，更新模板 route，追加页记录；涉及导航结构变化则追加平台记录 |
| API、重定向变化 | 根据实际业务影响归入已有页面/平台，不给接口或重定向单独编号 |
| 仅主站改动、客户资料/成本等业务数据操作、文档/技能/测试维护 | 不因此增加员工软件版本 |

同一正式发布中每个受影响目标合并为一条记录。普通更新递增小版本；确有大调整时才采用下一个大版本并说明理由。平台与页面独立编号，不把所有页面强行同步成同一版本。

## 修改与发布流程

1. **修改时确定范围。** 对照实际 diff 列出目标、变化类别和简短中英文说明。检查是否混有其他 Agent 未完成的改动，发布内容必须与本次记录一致。仅完成代码或预览时，保留待发布说明并在交付中注明，不能提前写入正式历史。
2. **发布前验证。** 运行与改动相关的检查，确认原业务功能和访问权限正常；涉及版本机制时参考维护文档中的版本、导航、RLS 和浏览器测试。正常页面更新无需重新建表或运行初始化 seed。
3. **确认正式上线。** 按当前任务的发布方式核对员工站生产域名实际服务的版本和修改后的功能；候选部署成功或预览通过不等于生产上线。未上线、上线验证失败的候选版本不写成功记录。已生效后又回退的版本如实记录发布和回退，不抹去历史。
4. **追加数据库记录。** 生产验证通过后读取最新版本，准备实际 old → new 版本、中英文标题/说明与真实发布时间。使用事务锁定受影响 targets，多个目标按固定 id 顺序加锁；锁定后复核预期当前版本，再追加 history。若当前版本与计划不一致，回滚并重新判断是否有其他发布，不能盲目重试递增。新增/下线/改名的 target 变更与对应页面、平台记录在同一事务完成。
5. **读回并核对。** 提交后重新查询 `staff_release_current` 和本次 history；确认目标、版本、说明、发布时间一致。检查 `/updates` 及受影响页面版本入口；纯记录追加无需再次部署应用。若缺少可用的员工登录环境，说明 UI 未验证，不声称已经验证。

记录说明面向员工，写清功能变化及其影响，中文和英文都要填写；不写客户 ID、邮箱、token、密钥或其他敏感数据。使用真实发布时间，不能把尚未发布的计划日期写进去；时间不确定时先查部署证据，不编造旧历史。

## 失败、重试和回退

- 历史只追加，不覆盖、不删除、不降低版本。说明纠错和代码回退也使用新版本，说明更正/回退内容。
- 写入响应超时或连接断开时，先用本次计划的 target、版本和说明查询是否已提交。完全一致则视为已经完成，不再新增版本；不同则查清并发发布情况，不能使用覆盖式 upsert。
- 不重跑 `supabase/seed-release-history.sql`，也不利用初次基线例外给后续候选部署提前记版本。
- 若代码已上线但记录写入失败，明确报告“已上线，版本记录未完成”，保留本次部署标识、目标、预期版本和说明，供恢复时核对。不要仅为记录失败回退正常业务；不要把数据库失败描述为整个发布已完成。

完成发布时报告：本次平台/页面版本变化、实际上线内容、记录读回及 UI 验证结果，并提供 [员工更新记录](https://staff.solortide.com/updates)。仅修改代码时报告待发布范围，不声称数据库已更新。
